## Design Context

### Users and jobs
OpsTracer serves on-call engineers, SRE/platform leads, and engineering leaders who coordinate incident response, preserve evidence, and explain root cause under time pressure. Product screens must support fast scanning, confident action, and dense operational data without visual noise.

### Product personality
Precise, calm, evidence-led, and compact. The authenticated application should feel like a dependable analytical instrument, not a marketing page or a stylized incident simulator.

### Product aesthetic
`index.html` is the current product design system and imports only `summation-app.css`. It is a reconciliation, not a clone: OpsTracer owns identity and domain semantics; the clean-room Summation audit informs component geometry, density, borders, elevation, and application composition.

- Preserve the production OpsTracer SVG lockups wherever a brand lockup is part of the source composition. Do not inject a logo into authenticated application chrome when the audited route does not contain one, and never replace a required mark with live text.
- Preserve Host Grotesk for human language and DM Mono for machine facts.
- Brand amber `#F0A439` is the single consequential action; secondary actions stay light and outlined.
- Product neutrals follow the audited Summation ramp directly: near-white `#FFFFFE` surface, `#FAFAFA` subtle surface, `#F6F6F6` components, `#EEEEEE` active/dividers, `#D1D1D1` control borders, `#363636` text, and `#6D6D6D` secondary text. OpsTracer identity comes from logo, typography, amber actions, and semantic state colours—not a cream background.
- Connector forms use shared control tokens: 44px primary fields with 12px inline padding and 8px radius; secondary schedule controls use a separate 32px compact density with 10px inline padding and 6px radius. Do not restate these values inside page-specific selectors.
- Actions use a shared 36/32/28px hierarchy: primary actions have 8px radius and 12px inline padding; default and compact actions have 6px radius and 10/8px inline padding. Nav/menu rows are 30–32px and tags are 18px. OpsTracer amber replaces Summation black only for the consequential primary action.
- Radius ladder: 6px compact controls, 8px primary fields/analytical nodes, 12px cards/menus/shell, 16px dialogs.
- Static product cards use only `0 1px 2px rgb(23 20 17 / 6%)`; stronger shadows are reserved for overlays.
- The dashboard composes reachability, source health, open incidents, and on-call ownership on the shared light surface. Do not add speculative KPI or chart modules without a product requirement.

See `SUMMATION-APP-UI-AUDIT.md` for route coverage and rendered measurements.

### Component generation contract
This contract is mandatory for every new screen, state, or UI component. “New” includes components imported from the live OpsTracer product and variants added to an existing family.

1. Inventory the shared foundations in `design-tokens.css` and the existing component families in `summation-app.css` and `index.html` before drawing or coding anything.
2. Reuse or compose an existing component whenever its structure and behaviour fit. Extend its shared variant API when the difference is reusable; never fork its measurements into a page-specific class.
3. Only when the inventory has a real gap, use `SUMMATION-APP-UI-AUDIT.md` and the visible authenticated Summation application as the geometry and interaction reference. Use `OPSTRACER-DEV-UI-AUDIT.md` only for missing OpsTracer workflows, content structure, and domain states.
4. Map every adapted pattern back to OpsTracer identity: production SVG logo, Host Grotesk, DM Mono for machine facts, amber only for the single consequential primary action, and the shared semantic state colours.
5. Promote any necessary new measurement to the shared token/component layer first, then use it in the page. One-off colours, type sizes, spacing, radii, shadows, borders, field heights, button heights, and icon treatments are prohibited.
6. Verify applicable default, hover, focus-visible, active, selected, disabled, loading, empty, validation/error, and responsive states before considering the component complete.

Do not copy Summation branding, proprietary assets, account data, or product copy. Summation is the visible style and geometry benchmark; OpsTracer remains the product identity and semantic source. If an existing component cannot be reused, document the mismatch before adding a shared primitive or variant.

### Marketing separation
`landing.html` remains the public-site system and imports `summation-refresh.css`. Product and marketing both import `design-tokens.css`, the sole source for brand fonts, neutral and semantic colours, spacing, radii, control sizes, and elevation. Marketing may use larger editorial type and section rhythm, but its component classes must never cascade into product components.

### Retired implementations
Do not reintroduce these implementations. Their OpsTracer concepts may remain in the system when restyled:

- warm-black panels and reverse-logo display cards inside the light application; evidence stays on the same light surface as every other operational component;
- decorative notches, decorative mono prose, or amber used for non-consequential actions; the approved compact evidence panel is the sole exception and may use one 18px bottom-right terminus cut;
- marketing capsule buttons/tabs, oversized 56–100px fields, or black selected-tab pills;
- bordered cards around every content group, nested card stacks, or visible double borders;
- legacy warm backgrounds, global dark-theme overrides, or generic selectors such as `.chip` that leak across systems.

### Component rules
- Data lists use one 12px rounded outer shell, a 40px quiet header, 78px content rows, and 0.5px internal dividers. Never draw borders around individual cells or nest another card inside the list.
- Every documentation section, intro, dashboard, list, and specimen uses the same 1376px content rail. Do not add component-specific max-widths that move section edges.
- Reusable work objects may use 143px cards with 12px radius; plain content should not.
- Product tab switches are 32px high with 28px items, 2px inset padding, 8px group radius, and quiet active fill. Sidebar/menu rows are 30px with 8px/6px radius.
- Every icon button has an explicit 24/32/36px hit box and a centered 14–16px outline icon.
- Tags use inline-flex centering, 18px minimum height, 6px horizontal padding, and `white-space: nowrap`.
- Form label → control → helper spacing is 6px; fields use consistent inline padding.
- Evidence timelines use the approved three-event compact pattern: a 40px quiet header, 40px row rhythm, 42px footer, and one 18px bottom-right terminus cut. Time width, track width, track centre, and column gap are shared variables; both the vertical rule and every dot derive from that same track centre.
- Workflow inspectors sit 16px clear of both rail edges and keep 16px internal padding. Definition rows use dividers only between items; never leave a trailing divider that creates a false empty row.
- Settings use one 1200px shell with a 200px grouped rail, 32px navigation rows, 16px shell radius, and centered 668px content; data-heavy Users and Usage panels may expand to 808px. Profile value rows are 80px, integration rows 72px, member tables use 40px headers with 58px rows, and loading uses the same panel geometry as loaded content.
- Colour never carries state alone; semantic colour always appears with a written label.
- Use the same outline icon family generated between the icon-token markers in `index.html`. Run `node tools/build-icons.mjs` after changing local SVG sources.
- Maintain semantic HTML, named icon actions, visible focus, text alternatives for any future data visualisation, and reduced-motion support.

### Responsive behaviour
The desktop product shell uses a 252px sidebar and a white main shell with 10px outer gutters. The catalog follows the live OpsTracer application's centred 1376px rail. Below 820px the sidebar becomes a drawer; analytical and form grids collapse to one column; wide tabular rows scroll inside their list region rather than widening the page.
